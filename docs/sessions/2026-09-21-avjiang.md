## INFRA — 90% of prod MySQL query volume is not the application (and the crons are innocent)

Investigated a constant ~2,830 queries/hour floor on prod MySQL that persists 24/7. Least-squares
over 4,032 five-minute buckets across 14 days gives `Queries/5min = 278.2 + 3.395 × Requests/5min`
(Pearson r = 0.484): a constant floor of ~2.4M queries/month independent of app traffic, with the
app costing a healthy 3.4 queries per HTTP request. In the four buckets with **zero** App Service
requests, MySQL still ran 245 queries/5min. The floor is also dead flat straight through 02:00,
02:30, 03:00 and 04:00 WIB, so `src/cron/cron-manager.ts` is not responsible. App-attributable
share of 1,240,069 queries over 14 days: 9.5%. Recorded in the runbook's findings section along
with the two ways to confirm attribution during the Phase 3 night window.

Separately, `memory_percent` on prod MySQL has climbed monotonically 37.17% → 46.91% over 31 days
(+1.67 pp/week recently, ≈+200 MB/month on 2 GiB) with `Uptime` at 44.5 days continuous and no dips.
Not buffer-pool warming (`innodb_buffer_pool_size` fixed at 512 MiB, allocated at startup) and not
data growth (`storage_percent` flat at 4.6%).

**Why:** the query floor and the resulting ~50 GiB/month `network_bytes_egress` looked like a
serious application bug against a 0.93 GB database, and it was the main argument against moving
MySQL off Azure. Establishing that it is server-side removes that objection and, more importantly,
avoids a pointless hunt through the cron code.

**Gotcha:** `.claude/memory/reference_infra_capacity.md` still says MySQL `memory_percent` is
"pinned ~38% with near-zero variance ... flat is healthy; it will not track load." That was true in
June/July and is now **false** — it has been climbing for 31 straight days. Do not use that memory
file to dismiss a memory reading. Also: Azure's exported metrics cannot distinguish
`Com_show_status` from `Com_stmt_execute`, so metrics alone can never attribute the floor to
platform vs Prisma — that needs `SHOW GLOBAL STATUS LIKE 'Com_%'` on the server. Finally, when
reading `active_connections` at sub-hour granularity, use `Maximum` not `Total`: `Total` sums the
per-minute samples and makes ~8 connections look like 40.
